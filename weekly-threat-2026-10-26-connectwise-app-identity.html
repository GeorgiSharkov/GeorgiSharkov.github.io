CLOUD IDENTITY / SUPPLY CHAIN / WEEK 44

When a trusted application becomes the intruder

The ConnectWise credential campaign through a SOC lens: follow the application identity, investigate new credentials and role grants, and separate evidence of access from evidence of data theft.

Published 26 October 2026 / Research window: 19-26 October / Technical walkthrough: approximately 10 minutes

Evidence standard: Microsoft attribution is identified as an assessment. The investigation workflow and queries below are original analyst guidance, not claims about telemetry from your environment.

This week's signalTechnical mechanismTimelineInvestigationHunt queriesRemediationEvidence

01 / WHAT CHANGED

A fresh assessment of an existing intrusion

On 21 October, Microsoft attributed the ConnectWise multi-tenant application compromise to Storm-0940 and described use of the ARTEX agent framework. It reported authentication through previously authorised applications and subsequent Graph reconnaissance, credential changes and attempted privilege changes. Microsoft explicitly cautioned that application presence or successful authentication does not establish data access or exfiltration. [1]

Huntress's follow-up distinguishes what its tenant logs show from what they cannot prove: its telemetry supports a mix of scripts and operator-directed activity, but does not independently establish the presence of a language model. It also identifies an important visibility gap around Graph reads in the tenants it examined. [2]

CyberShark assessment: prioritise the identity trail over the AI label. A suspicious service principal gaining a new credential or role merits investigation whether a human, script or agent issued the request. Build your case around durable evidence: which identity acted, against which resource, with what result and what changed afterwards.

02 / TECHNICAL BREAKDOWN

Three objects to keep separate

Think of the application ID as the product identity you search across tenants. The tenant's service principal is the local representation whose permissions and activity you investigate. A credential identifies a means of authentication. [6] Record each separately; a display name alone is a poor join key when names can change or several integrations look similar.

In this campaign, Microsoft's account describes misuse of application trust rather than an interactive user sign-in. [1] The practical implication is that a review limited to employee logins can miss the relevant activity. Start with workload authentication and then examine changes made by that workload identity.

Investigation hypothesis: a second credential planted in a different application could survive remediation of the original integration. Test that hypothesis against the directory audit trail. Do not conclude persistence merely because a credential exists: resolve who created it, the target object, the approved change and whether it was subsequently used.

04 / FIRST ANALYST PASS

Build an identity ledger before joining events

Create one row per tenant and relevant integration. Capture application ID, local service-principal object ID, account state, owners, consent and permissions, known credential identifiers, and the person responsible for the integration. Establish the same identifiers for every downstream application that appears in suspicious change events.

Two application IDs corroborated across the incident reporting are 506e08f9-6e9a-4da4-942b-a099a03644ae and 24205314-2b89-4e07-a2a4-579e898a5640. They identify legitimate integrations, not malicious binaries. These two IDs are a starting set, not an exhaustive inventory of the vendor's application family. [3]

  • Exposure: was the integration authorised during the review window? Current absence alone does not answer historical exposure.
  • Authentication: separate successful requests from failures, preserving the original result value and resource context.
  • Modification: identify application credentials, ownership, consent or privileges changed by the identity. Record original event IDs.
  • Impact: investigate resource activity independently. Describe missing logs as a visibility limitation, not proof that access never happened.

Use an initial review window covering the reported activity, then widen it when retention permits or earlier suspicious events appear. Preserve the exact UTC boundaries and exported filters so another analyst can reproduce the search.

05 / DEFENSIVE QUERY STARTERS

Hunt the application, then follow its changes

These original Microsoft Sentinel / Log Analytics examples use the documented AADServicePrincipalSignInLogs and AuditLogs tables. They require existing ingestion and retained records. They have been checked against the documented fields, but have not been executed against a customer workspace. Inspect your schema, permissions and costs before running broad searches. [4] [5]

A. Review workload sign-ins without suppressing failures

Replace or extend the application list using your verified inventory. Resolve the result values in your own tenant; the query deliberately preserves them rather than assuming one success encoding.

let WindowStart = datetime(2026-10-13T00:00:00Z);
let WindowEnd = datetime(2026-10-27T00:00:00Z);
let Applications = dynamic([
  "506e08f9-6e9a-4da4-942b-a099a03644ae",
  "24205314-2b89-4e07-a2a4-579e898a5640"
]);
AADServicePrincipalSignInLogs
| where TimeGenerated >= WindowStart and TimeGenerated < WindowEnd
| where AppId in (Applications)
| project TimeGenerated, AppId, ServicePrincipalId,
          IPAddress, ResourceDisplayName, ResultType,
          ResultDescription, CorrelationId
| order by TimeGenerated asc

B. Follow changes initiated by a local service principal

Set LocalSpObjectId to the tenant-specific service-principal object ID, not the application ID. The dynamic initiator shape and operation labels must be verified in your exported records. Review all returned changes before narrowing operation names.

let LocalSpObjectId = "REPLACE_WITH_VERIFIED_OBJECT_ID";
AuditLogs
| where TimeGenerated >= datetime(2026-10-13T00:00:00Z)
    and TimeGenerated < datetime(2026-10-27T00:00:00Z)
| extend InitiatorSp = tostring(InitiatedBy.app.servicePrincipalId)
| where InitiatorSp == LocalSpObjectId
| project TimeGenerated, OperationName, Result,
          InitiatedBy, TargetResources, CorrelationId, Id
| order by TimeGenerated asc

Next pivot: expand the returned target resources and inspect modified properties. Resolve each changed object before linking it to subsequent authentication. Correlation IDs are useful context, but a shared time window alone is not a causal join. Preserve the raw event alongside your interpretation.

06 / ATT&CK MAPPING

Attach the technique to the evidence

These are analyst mappings of the reported behaviours, not assertions that every tenant exhibits the entire chain.

  • T1078.004 / Cloud Accounts: investigate use of an established cloud identity outside its expected operational context.
  • T1098.001 / Additional Cloud Credentials: apply when evidence supports an unauthorised credential addition, not merely the discovery of an old secret.
  • T1098.003 / Additional Cloud Roles: map supported privilege or role manipulation, preserving the actor, target and change result.

Keep the attribution field separate from the technique field. A suspicious role assignment can justify containment even when attribution to Storm-0940 remains unconfirmed for your case.

07 / FALSE POSITIVES AND BLIND SPOTS

Do not turn a weak pivot into a verdict

A backup provider can legitimately authenticate frequently, rotate credentials or perform directory queries. Validate those actions against owner confirmation, change records, expected resource access and historical patterns. A familiar display name cannot validate an unexpected credential addition.

A Python or curl user agent is a triage clue, not an AI detector. In its original investigation, Huntress also warned that public IP lists can mix different activities and that internal cloud addressing complicates simple source-IP pivots. [3]

Write separate findings for confirmed unauthorised authentication, confirmed configuration changes, and confirmed resource access. If evidence is unavailable, name the missing source, retention limit and resulting unanswered question. This makes the handoff actionable without overstating impact.

08 / CONTAIN, REPAIR, VERIFY

Close the trust path and look for a second one

Microsoft's published guidance is to keep affected connections disabled pending formal vendor restoration instructions, preserve evidence and avoid deleting enterprise applications as the first response. Recheck the current advisory before restoration because vendor guidance can change. [1]

  1. Assign ownership: nominate an incident lead and a workload owner. Identify backup or restore dependencies before changing the integration.
  2. Preserve evidence: export relevant sign-in and audit events, configuration, permissions and credential metadata. Capture identifiers and expiry dates; do not export secret values into case notes.
  3. Contain: disable the affected trust path through an approved procedure. Document the time and expected operational impact.
  4. Remove unauthorised persistence: examine downstream credentials, owners, role assignments and grants. Coordinate credential removal or rotation with the application owner.
  5. Validate: confirm the intended account state and permissions, then monitor for fresh suspicious authentication or changes. A quiet dashboard is insufficient if ingestion stopped.
  6. Restore deliberately: follow current vendor instructions and record approval. Test backup and restore functions as well as identity controls.

Escalate promptly when evidence supports an unauthorised successful sign-in, unexplained privileged grant, or suspicious credential addition. Prioritise the combination of a demonstrated identity action and meaningful access over an isolated low-confidence infrastructure match.

09 / SHIFT HANDOFF

Six fields that keep the next analyst moving

  • Tenant and verified application / service-principal identifiers.
  • First and last relevant events, with UTC times and raw event IDs.
  • Authentication outcome, changes observed and independent impact evidence.
  • Containment completed, credential or permission changes still pending.
  • Visibility gaps, queries used and the next evidence collection owner.
  • Restoration criteria, monitoring window and customer update deadline.

Example reporting structure, not incident evidence: “We confirmed [identity action] in [tenant] at [UTC time]. We observed [configuration change / none identified within available logs]. Resource access remains [confirmed / unconfirmed / limited by retention]. We completed [containment] and are validating [remaining trust path].” Replace every bracket with supported case findings.
